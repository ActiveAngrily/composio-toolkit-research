100 apps → an agent toolkit build queue

Composio already covers 56 of these 100. This is an account of the other 44 — what credential each needs, whether it can be obtained without talking to a human, and how far the answers can be trusted.

source repository· data.json· llms.txt· 100 apps, 580 citations, ~25 min of compute

Abstract

Before building a connector, the four questions that matter are: what credential does this app need, can it be obtained without a human, how large is the API, and is it worth building. This work answers them for 100 apps using an agent running inside Composio's own remote workbench, and then spends most of its effort on a harder question — how would we know if the answers were wrong.

Every claim carries a verbatim quote, that quote's URL, a source-authority tier, and a verdict from re-reading the page. 71 claims failed that check and were quarantined to unknown rather than reported. Accuracy is reported as two numbers per field, never one, because a pipeline that answers nothing scores perfectly on precision alone. An independent cross-check against Composio's own registry — 56 apps, no model involved on either side of the comparison — puts auth agreement at 75.0% token-level and 83.9% family-level.

No human verified any of these answers. That limitation, and what stands in for it, is stated in §8.

1Findings

Six, in the order a reader deciding what to build would want them. Every number is computed from the dataset at build time, not transcribed.

1.1Which auth dominates is the wrong question.

39 of the 100 accept both an OAuth dance and a static secret, 34 accept only a static secret, and just 12 force OAuth. 73 of 100 have a static-secret path, so for most of this list the expensive part — registering an OAuth application with each vendor — is optional. The histogram everyone reports (OAuth2 leads at 51) is a fact about labels; the split above is a fact about what it costs to ship.

1.2The coverage gap is shaped, not random.

Productivity 9/10, Developer 8/10 are nearly complete, against Ecommerce 2/10, AI-native 3/10. The thin categories are the newest ones, where the vendors themselves are newest — so the gap is a function of vendor age, not of difficulty, and it will keep opening in whichever category is youngest at any moment.

1.3The most common blocker is money, not partnership.

Of the apps with a blocker: 13 need a paid plan, 8 need vendor app review, 8 need a sales or partner conversation, and 2 have no public API at all. A paid seat is a purchase order; a partner gate is a quarter. Ranking the queue by blocker kind rather than by count is what makes it actionable.

1.4The dangerous error is not an invented sentence. It is a real sentence about the wrong product.

Quote validation cannot catch this class, because the quote is genuinely on the page it cites — the page is just about something else. A name-mention check caught 24 claims sourced from non-vendor pages that never name the app, 2 MCP claims whose evidence never mentions MCP (a pass-2 re-query had already repaired most of that class — §6.1), and 3 one-liners that were authentication instructions. All quarantined. iPayX's description welcomed the reader to iPaymu; Sherlock's “official MCP server” belonged to the Covertlabs infostealer platform; GoHighLevel's entire access story was lifted from n8n's documentation. This is the same failure mode as matching Plaid to a Composio toolkit slugged placid.

1.5A tool count measures the integrator, not the app.

On the 5 apps where both a Composio tool count and the app's own OpenAPI document could be read, the two disagree by up to 165× (Table 5). A tool count is a coverage decision — it answers “how much of this have we wrapped”, not “how big is this”. This project had been using it for the second, which is why breadth is now labelled by source instead of merged into one scale.

1.6Someone else has already built most of the missing integrations.

25 of the 44 apps missing from Composio's catalog claim an official MCP server, and 22 of those 25 rest on evidence from the vendor's own domain rather than a third-party directory — both numbers are published because a front-page figure that a directory can inflate is not a finding.4 Nobody asked this question in the first pass: the column was 24% answered until a query was written for it, and it is now 82%.

2Which categories are self-serve, and which are gated

The brief asks this question by name. Access is not asked of the model as one question — it is derived by rule from four separately evidenced sub-answers, and the basis for every value is in the row detail in §4.

Read the pale segments as the real finding. Access is the least-answered column in this dataset (24–42% across its three sub-fields), and it is the column a build queue most needs. Which pricing tier includes API access is the single thing vendors publish least.

3The build queue

The 44 apps Composio does not have, grouped by verdict and ordered by what they cost. Build now means self-serve credentials and a documented API today. Caveats means buildable once something is bought, reviewed or consented to. Outreach means a human conversation before any code.

5Method

Three lanes, deliberately independent. Two of them contain no language model at all, which is what makes the third one checkable.

What the agent is told

Every answer must arrive with a verbatim sentence copied from a page it actually opened, plus that page's URL — or the answer is unknown. It is told that an automated checker will re-read every URL, so inventing a quote scores strictly worse than admitting ignorance. Abstention is cheap; confident error is expensive.

The extraction model is a GPT-family model running in Composio's workbench, a different vendor from the Claude session that wrote this code. The cross-checks are therefore cross-vendor rather than a model grading itself.

Derivation is not the model's job. Auth family, access and the buildability verdict are computed by rule from the evidenced fields, and every row carries the rule that produced its value, so a reviewer can disagree with the rule rather than with an opaque answer.

Where a human was needed

Catching the deterministic lane lying. The registry matcher paired Plaid with a Composio toolkit slugged placid at 0.909 similarity. Placid is an image-generation product. One false positive, caught only because fuzzy matches were flagged for review rather than trusted. The lane with no model in it produced the wrong answer.

Deciding what a schema may not say. Mermaid CLI came back with Bearer, JWT, OAuth2, REST and an official MCP server. It is an npm package that renders diagrams locally. Every value was invented — because the schema offered unknown or a guess, and nothing for “not applicable”. A person had to notice the shape of the error, not the error.

Refusing a flattering number. The first unknown-accounting run reported that 98% of the gaps were genuine vendor non-disclosure. That was an artefact of a default value, not a measurement. See §7.

Reading the rendered table. Two wrong answers survive every automated check in this project and were found by eye (§8).

6Verification

Two numbers per field, because one of them can be gamed. A pipeline that answers nothing scores 100% on precision, so coverage is published beside it — and the honest reading of Table 3 is that coverage is this project's weakness, not correctness.

Two rows read like holes and are not. product_class and primary_blocker are marked by rule: they are derived from the evidenced fields above them, not claimed by the model, so there is no quote to verify by design. Pass 1 did ask for a blocker but asked for a free-text reason instead of a quote, which is why that row shows 7.2% rather than zero.1

A third lane: ask the server, not the docs. Every app got an unauthenticated probe of its API base and a GET /pricing that follows redirects. Across 100 apps the redirect probe found exactly one sales gate: Pylon, the case it was designed from. That is a negative result and it is published as one — a technique built from one vivid example generalised to nothing, which is itself the finding. What it did establish: 50 apps publish pricing at a predictable URL, 28 have no /pricing at all, 5 block automated requests, and 9 expose a machine-readable OpenAPI document.

6.2The number that got worse

Agreement with Composio's registry fell. From 82.1% to 75.0% token-level, across three successive tightenings of what counts as evidence. Pass 1's score was partly propped up by answers that were right without being evidenced; quarantining the unevidenced ones removed correct answers along with the wrong ones. Precision up, recall down. A verification pass in which every number improves is a verification pass nobody should trust.

6.3The 75 claims we refused to guess about

Pass 1 showed the model 5,000 characters per page and retained 2,500, so 75 claims became unverifiable offline — a quote from the back half of a page simply is not there any more. The tempting move was to call them fabrications. Instead they were labelled truncated-evidence, excluded from both sides of the ratio, and the 53 pages behind them were re-pulled in full.

53 were verbatim, 21 were real sentences reformatted, and 1 was fabricated. Counting them as errors would have moved the published error count from 71 to 145 — a 2.0× overstatement of the problem this pass claimed to be fixing.2 That is the clearest argument in this project for labelling uncertainty rather than resolving it in whichever direction flatters the story.

7Where the agent was wrong

5 of the 14 are our own schema, not the model: we recorded the envelope (Bearer, Basic) where Composio recorded the credential kind (API key). Collapsing that distinction moved agreement from 75.0% to 83.9% — the first fix that improved accuracy was to the measuring instrument, not to the pipeline. The remaining 9 are real recall misses.

The finding we deleted. An early run announced that 98% of the blanks were genuine vendor non-disclosure and 0% were our own retrieval failure. It was false. Pass 1's prompt never asked the model why it abstained, so the accounting was stamping “not stated publicly” on every case where we had pages and no answer — a claim about vendors, manufactured out of our own silence. The honest version was 75 of 498 blanks provably our own gap — every missing MCP answer, because pass 1 issued three queries per app and none of them asked about MCP — and 311 unclassified until the model is asked to name its reason. That is worse for us and truer. Pass 2 then wrote the query pass 1 never issued and closed all 75 of them, which is why that figure is 0 today — the one category of blank we could prove was ours is the one category we were able to fix.

8Limitations

No human verified any of these answers. The brief asks for a by-hand cross-check, and it was not done. The blank sheet is in the repository at outputs/human_audit.csv with its sampling rule pre-registered in agent/audit.py before any result existed — stratify by verdict, then take the app with the fewest evidenced fields and the app with the most from each stratum, deliberately over-sampling the weakest claims. It is unfilled. Every accuracy number on this page is therefore machine-checked. What stands in for the human check is the 56-app registry cross-check in §7: it covers roughly three times more apps than the planned hand-audit would have, and it is independent of the model in a way an audit run by this project's own author would not have been.3 What it cannot substitute for: quote fidelity is verified throughout, but factual correctness where no page states a thing plainly is not.

What is missing from the data

Access coverage is 24–42%. Which pricing tier includes API access is the field vendors publish least and the field the build queue most needs. The re-query for it was designed and cut for time — that is a scheduling decision, not a finding about vendors.

Breadth is unknown for 40 apps. The 56 in Composio's catalog have a tool count and 5 more have a readable OpenAPI document; per finding 1.5 those two are not the same measurement, so the column is labelled by source rather than merged into one invented scale.

311 abstentions are unclassified. Pass 1 never recorded why it abstained, so “the vendor does not publish this” cannot be separated from “we did not find it”. Naming that is cheap; fixing it needs another pass.

No no-retrieval baseline was run. The improvement story runs pass 1 → pass 2, which is real, but it would be starker against a naive anchor.

Apps and cases that defeated us

Two name collisions this project's own validator cannot catch. Mermaid CLI's “official MCP” resolves to mcp.mermaid.ai — Mermaid Chart, a commercial product, not the npm package the brief points at. Paygent Connect's description belongs to a different product on a lookalike domain that passes every authority test here. Both share a brand name with the right answer, which is precisely the case a name-mention check is blind to. Found by reading the rendered table — which is the argument for presenting data where a person can see it.

Mermaid CLI, Sherlock, higgsfield. Not APIs. Local command-line tools. The correct finding is “wrap the CLI”, and the first schema could not express it, so the model invented an API for one of them.

Stripe. Its documentation says API key, its server answers WWW-Authenticate: Basic, and its body says “You did not provide an API key.” All three are true; a docs-only pass picks one and looks wrong to anyone who knows another.

Composio's own Browser Tool. Documented as free and no-auth; returns 403 temporarily disabled by the administrator. A documented-versus-actual gap, found inside the product this research is for.

This page broke its own deployment. Brex's auth documentation contains the literal string Bearer {{your user_token here}}. Quoted verbatim, as the contract requires, it reached GitHub Pages, where Jekyll parses {{…}} as a template tag and failed the build — so the site silently served a stale commit. Fixed by disabling Jekyll rather than by editing the quote: the evidence is the artefact, and it stays byte-exact.

9Reproduction

Clone the repository and every number on this page regenerates. The tests need no key and no network.

one app python -m agent.run_research --app "Notion"
no model python -m agent.run_research --app "Pylon" --sources-only
registry python3 scripts/fetch_composio_registry.py
re-derive python -m agent.upgrade
pass 2 python -m agent.pass2
this page python -m agent.build_site
tests python tests/test_agent.py
audit sheet python -m agent.audit --sheet

The steps that need the network ran once: the URL-strict quote re-grade and the pass-2 repairs require Composio's workbench. Their results are committed as data/pass1_strict_grades.txt, data/pass2_patch.json and data/probe_patch.json, so any machine reproduces the identical dataset with no key at all. Verified on three Python versions (3.10, 3.11, 3.13).

Notes

  1. Grading primary_blocker was structurally impossible in pass 1: the extraction prompt asked for a free-text reason rather than a quote and a url, so 92 of 100 slots had nothing to validate. That single prompt-design choice accounts for almost the entire ungraded population, and it is the clearest example in this project of a schema causing an error and the model being blamed for it.
  2. The overstatement factor is computed at build time from the quarantine count and the refetch verdicts. An earlier version of this page hard-coded it as “3.5×”, which was true while the quarantine count stood at 30 and silently false once it reached 71. Three other numbers in the prose had drifted the same way — the MCP coverage figure, the access-coverage range, and the count of schema-caused disagreements. All four are derived now: on a page arguing that claims must be checkable, a typed constant is the wrong tool.
  3. The registry cross-check is independent in the way that matters here: Composio's recorded auth scheme is not model output, and it was written by people with no knowledge of this dataset. It is not a substitute for reading a vendor's documentation by hand, and it only covers auth — the fields with the worst coverage, access above all, have no independent check at all.
  4. 25 apps claim an official MCP; 3 of those rest on a third-party directory rather than the vendor's own domain (Pylon, PitchBook, higgsfield). The headline number is the claimed count, but the defensible one is 22.
